# 从任务到设计、实现与验证

本文件负责执行顺序；源码核验由 [源码规则](source-policy.md) 维护，
具体场景与完成标准由 [验收参考](lessons-and-acceptance.md) 维护。

## 1. 定位任务并选择深度

检查 Git 状态、相关页面/组件、现有主题、依赖锁与测试，保留用户修改和功能契约。
识别用户要的是评审、局部修改还是新建/明显重构；不要把同一套完整流程套到每个请求上。

**局部修改快路径：**定位受影响区域与操作路径 → 记录现有行为及本次成功条件 →
复用项目实现做最小改动 → 定向复验并交付。记录可只有几条，不要求整页设计稿或新报告。
没有新能力缺口时不进入上游选型；需要新的视觉判断或组件能力时，才进入相应参考和下面的步骤。
只调局部效果时保持范围外的数量、速度、轨迹及覆盖区域。

新建/明显重构先读 [前端工程要求](frontend-brief.md)，然后执行步骤 2–5。
评审或诊断执行必要的观察与判断，按用户请求交付发现，不自动实施修改。

## 2. 建立任务基线与本次验收场景

确认核心用户、任务频率、已有输入输出和关键约束。已有界面尽可能运行，
观察用户怎样找到目标、理解状态、执行操作并从错误恢复；区分观察、测量和假设。
无旧界面的新建任务先定义成功条件，不虚构改前截图或效率提升数据。

按 [效率与场景验收](lessons-and-acceptance.md#task-acceptance) 选出本次最可能出问题的条件，
写清“任务/条件—成功标准—验证方式”。局部修改用短清单，整体工作用简短场景表；
只覆盖本次改动涉及的路径，不机械展开所有数据、状态、视口组合。

记录原有任务的入口、查找与理解负担、必要步骤、等待及错误恢复；这些是后续方案比较的依据。
缺少会改变产品方向的事实时提问，其余可据项目证据作出可说明的判断。

## 3. 形成设计简报与关键布局取舍

读取 [视觉基线](visual-baseline.md)，说明目标任务、信息优先级、密度、主操作位置和既有品牌/主题约束。
用文字线框、已有截图标注或低保真草图表达关键屏的阅读顺序、分区和窄屏关系；
局部修改无需重新制作全页草图。

对存在合理备选的关键结构，说明采用方案、备选方案以及任务收益和代价。
例如分栏与单列、常驻操作与按需入口，应依据任务频率、可发现性、误触风险和空间约束选择。
保留原结构也需有依据；不强制凑固定数量的方案、精修稿或用户确认环节。
配色与圆角描述不能代替结构取舍，用户已明确的设计要求优先。

## 4. 按需筛选和核验组件

按 [组件决策](patterns-and-components.md#component-decision) 先查项目现有实现，再定位真实缺口。
初筛使用职责、现有依赖、版本记录与可信资料，淘汰不适合任务的类别；不为每个库写拒绝报告或下载源码。
对准备采用/实质定制的具体候选，才按 [源码规则](source-policy.md) 完成匹配版本的源码、API、依赖与许可核验。
未读取源码时不能声称已核验实现，也不能把初筛印象当作具体 API 或兼容性事实。

从技能目录明确选择来源，例如：

```sh
python scripts/ui_sources.py fetch --source shadcn-ui
python scripts/ui_sources.py inspect --source shadcn-ui --file apps/v4/registry/new-york-v4/ui/dialog.tsx
```

缓存已有且完整时可直接核验/查看。日常任务不全量获取来源；专项组件只读对应参考。
组件决策记录与方案规模相称，保留采用、复用或拒绝的关键理由即可。

## 5. 实现、复验并交付

依托已有或选定组件和语义 token 实现。清楚区分上游原语、项目组合与主题适配；
遵守入口中的业务、安全和授权边界，不顺带迁移状态、数据、权限或构建体系。

按步骤 2 的场景清单运行交互、工程和视觉检查；出现新的相关风险时补入清单并复验。
检查实际渲染与任务完成情况，针对可观察问题修复；完成条件和证据边界见验收参考。
关键操作不可达、必要状态缺失或业务契约回退时继续修复，不能用配色、密度或构建指标抵消。
缺少条件时如实列出未验证部分，不把假设标为通过。

达到条件后交付关键取舍、功能/视觉/效率的实际结果与残余限制，并清理本任务无用临时产物。
无需另外复制规则或强制生成报告；只有用户要求维护本技能时才更新本技能和锁定清单。
