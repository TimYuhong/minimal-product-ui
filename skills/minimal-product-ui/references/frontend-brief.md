# 用户提供的前端工程提示词

新建界面、整页调整或前端选型时，先阅读本参考。
下面保留用户提供的原文，作为本技能的工程与体验要求，不是额外的依赖安装指令。

## 原文

> 你是一名资深前端工程师，具备优秀的 UI/UX 设计能力。请遵循以下规范：
>
> 优先复用成熟组件库，避免重复造轮子，确保组件源码可控、易于维护。
>
> 统一设计语言，保持颜色、字体、间距、圆角、图标和动画风格一致。
>
> 追求高质量视觉效果，页面简洁现代、布局合理、交互流畅，避免过度装饰。
>
> 严格控制依赖，按需安装，不重复引入功能相似的库。
>
> 保证功能完整，支持响应式布局、交互反馈及必要的加载、错误和空状态。
>
> 推荐技术栈：
>
> UI 组件：shadcn/ui、Radix UI
>
> 视觉组件：Magic UI、Aceternity UI
>
> 图标：Lucide React
>
> 动画：Motion
>
> 样式：Tailwind CSS
>
> 布局：react-resizable-panel
>
> 拖拽：dnd-kit
>
> 状态管理：Zustand
>
> 数据请求：TanStack Query
>
> 图表：Recharts
>
> 开发要求：
>
> 优先检查现有项目和依赖，复用已有组件，按需选择技术方案。保持代码简洁、结构清晰、性能良好，并在完成后验证功能和构建。
>
> 最终目标：用最少的必要代码和依赖，实现生产级的视觉效果、交互体验与工程质量。

## 与本技能一起执行

- 根据产品、既有设计语言和实际问题选择视觉方向；纯白/深色是可选基线，不是原文要求的唯一表达。
  用 [组件决策](patterns-and-components.md#component-decision) 落实主动复用与选型，
  用 [视觉审查](lessons-and-acceptance.md#visual-review) 检查最终效果。
- 原文中的“推荐”表示候选，不要求全部安装、迁移现有技术栈或重复引入相似库。
  后续补充的 HeroUI、React Bits 仍按各自职责与使用边界参与选型。
- 原文保留 `react-resizable-panel` 的写法。实施可调分栏前核对准确包名、版本和官方 API；
  现有组件参考列出的候选为 `react-resizable-panels`，不要未经核实照抄名称安装。
- 组件来源与实际 API 必须符合 [source-policy.md](source-policy.md)，不能只凭这段提示词猜实现。
  具体选型条件见 [patterns-and-components.md](patterns-and-components.md)。
- “生产级”是需要用功能、构建、响应式和交互验证证明的目标，不能以使用某个库直接宣称达成。


## 可执行的 UI 设计与实现补充

原文中的“复用成熟组件”“统一设计语言”“保证交互反馈”是目标要求。执行时应进一步落实为可检查的工作步骤。详细组件取舍见 [共享组件与卡片体系](patterns-and-components.md#component-reuse)，视觉基线见 [视觉方向与可选基线](visual-baseline.md)，最终验收见 [组件复用与细节验收](lessons-and-acceptance.md#component-acceptance)。

### 适用范围

- 新建页面、明显视觉重构、跨页面统一：执行完整的范围盘点、设计取舍、组件复用、状态检查和真实界面验收。
- 局部修复：只检查受影响组件、相邻布局和相关状态；不借机重做整页或引入新库。
- 评审/诊断：先给出源码或界面证据与问题，不把评审请求当作修改授权。

### 实施要求

1. **先看真实项目。** 检查 Git 状态、路由、页面、组件目录、实际导入、主题 token、样式入口、依赖版本和测试。保留用户修改、业务输入输出、权限、安全边界和现有功能。
2. **先盘点再设计。** 按本次范围列出真实页面、重复 JSX/CSS、现有卡片和小组件。明确哪些直接复用、抽取共享实现、只调样式、保持不变或暂时无法确认。不要只处理提示词点名的示例，也不要虚构不存在的组件。
3. **卡片按职责复用。** 多处存在相同职责和结构时，复用现有 Card 或建立共享基础与少量语义变体/组合组件，统一表面、标题、内容、辅助信息、状态、操作区和间距。不得强制卡片化；不得用复制 JSX/CSS 冒充复用；不得建立承载大量互斥布尔属性的巨型组件。
4. **小组件按实际范围完整检查。** 检查本次范围内确实存在且需要优化的状态徽标、复制反馈、验证、筛选、选择工具栏、输入控件、菜单、提示和其他业务小组件。按职责统一尺寸、内边距、图标、文案、边框、颜色、对齐、点击区域和反馈；不把示例列表当成封闭清单。
5. **视觉与布局服从现有设计系统。** 沿用项目的字体、颜色角色、spacing、圆角、边框、阴影、图标、主题和动效约定。检查页面容器、分区、卡片间距、卡片内边距、控件组、图文间距、基线对齐、留白和窄屏重排。不要为了“现代感”添加无意义色块或装饰。
6. **逐类检查交互状态。** 按职责检查适用的默认、悬停、焦点、按下、选中、禁用、加载、空、成功、错误、验证失败、确认中等状态。验证真实行为、就近反馈和恢复路径；不适用的状态说明原因。
7. **核验真实源码。** 先检查项目内部已有组件和依赖。对准备采用或实质定制的第三方组件，遵守 [source-policy.md](source-policy.md)，核对匹配版本的实现、类型/API、样式、依赖和许可；记录来源与实际调用，不以 README 或演示截图代替源码。
8. **运行真实页面并复验。** 启动实际路由，按任务检查相关桌面/窄屏、主题和状态；实际打开并查看截图，操作主流程和受影响交互，检查控制台、溢出、遮挡和焦点。修复高影响问题后在相同条件复拍复验。
9. **如实交付证据。** 区分源码检查、自动化行为、真实浏览器操作、截图视觉审查和真实业务结果。列出共享组件定义与调用点、小组件盘点、状态矩阵、测试结果、截图条件、未验证项和残余风险。构建成功、mock 成功或截图文件存在都不能单独证明 UI 通过。

### 可直接用于 Codex 的任务提示词模板

将方括号内容替换为本次任务的真实信息；局部任务应缩小范围，不要将模板变成全站重构授权。

```text
$minimal-product-ui

请基于当前项目真实源码，完成以下 UI 设计与实现任务。目标是改善真实页面的视觉一致性、组件复用、细节、交互和运行效果，不是只给设计建议或替换颜色。

任务目标：[填写]
目标路由/页面：[填写]
修改范围：[填写]
必须保留的功能、数据契约和设计约束：[填写]
依赖限制：[填写]
验收重点：[填写]

执行要求：

1. 先检查 git status、项目结构、路由、组件目录、package.json/锁文件、主题 token、样式入口、现有 UI 库和测试；不得覆盖用户已有修改。
2. 盘点本次范围内真实存在的页面、卡片、小组件、重复 JSX/CSS、组件导入和交互状态。不要只修改提示词点名的少数示例，也不要虚构项目不存在的功能。
3. 先复用项目已有实现。对相同职责、结构和交互的卡片，优先使用同一共享 Card 基础/语义变体或组合组件；统一表面、标题、内容、辅助信息、状态和操作区。卡片是否使用由真实内容决定，不要强制卡片化。
4. 对本次范围内所有确实需要优化的小组件逐项检查：尺寸、内外边距、图标、文案、颜色、边框、圆角、对齐、点击区域、焦点、状态和反馈。按职责统一，不局限于几个示例。
5. 沿用项目已有视觉 token 和主题；检查页面容器、分区、卡片间距、卡片内边距、控件组、图文间距、基线对齐、密度、长文本和窄屏布局。
6. 按组件职责检查适用的 default、hover、focus、pressed、selected、disabled、loading、empty、success、error、确认/验证等状态。真实操作验证状态变化、反馈和恢复路径；不适用项说明原因。
7. 对准备采用或实质定制的第三方组件，先核对项目版本，再按 Skill 的 source-policy 阅读匹配版本的真实源码、类型/API、样式、依赖和许可。列明来源、版本、文件和实际调用；不得凭截图或 README 声称复用官方组件。
8. 启动项目并打开实际路由，按本次任务检查相关桌面和窄屏、主题及关键状态。实际打开查看截图，操作主流程和相关交互，检查控制台、溢出、遮挡、滚动和焦点。
9. 修复发现的高影响问题，并在相同路由、视口、主题和数据/状态下重新截图、查看和复验。
10. 最终交付：修改文件；共享组件定义与实际调用点；小组件盘点和状态矩阵；实际测试的路由/视口/主题/交互；构建与测试结果；截图位置；已验证、失败、未验证和不适用项。

不得为了视觉统一删除业务功能；不得复制相似 JSX/CSS 冒充组件复用；不得把构建成功、mock 成功或截图文件存在当成视觉验收通过。缺少源码、浏览器或真实业务条件时明确标记未验证，不得伪造结果。
```

### 使用边界

- 组件名、卡片类型和小组件示例用于帮助发现问题，不是固定安装或实现清单。
- 不要求所有页面采用相同布局、配色、卡片数量或动效；统一的是相同语义和职责的视觉/交互规则。
- 不为满足“复用”而抽取只使用一次且没有稳定共性的组件；也不允许重复实现已存在的成熟组件。
- 详细验收标准以 [组件复用与细节验收](lessons-and-acceptance.md#component-acceptance) 为准，避免在提示词中复制一份独立标准。
