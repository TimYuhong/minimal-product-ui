# 视觉审查与长期验收

此处维护验收闭环与判定标准；组件决策见
[patterns-and-components.md](patterns-and-components.md#component-decision)，不在两处重复选型规则。

<a id="task-acceptance"></a>

## 先定义本次要证明什么

在实现前按实际任务选定成功条件，局部修改可以用几条清单，整体改造用下面的简短记录即可。
任务目标、数据和约束保持可比；发现新的相关失败条件时补入并复验，不机械穷举所有状态组合。

| 核心任务与频率 | 现状及证据 | 方案收益与新增成本 | 场景、成功条件与验证方式 | 改后结果与限制 |
|---|---|---|---|---|
| 用户要正确完成什么 | 真实操作/截图/测量；无基线则注明 | 影响哪个任务，为什么值得取舍 | 指定数据、视口或事件序列，以及怎样判断完成 | 已验证/失败/未验证；观察与假设分开 |

### 效率是正确完成任务的整体成本

同时看找到目标、理解标签和状态、准确输入/操作、等待和滚动、误触与失败后的恢复。
点击数、首屏数量、目标尺寸和耗时只证明各自观察到的维度，不用任意权重合成“效率分数”，
也不把自动化脚本耗时当成人类任务时间。

- 先确认任务能正确完成，信息可读、动作可发现、错误可恢复；再比较步骤、等待和空间成本。
- 允许有依据的整体收益取舍：例如低频危险操作增加一步，可由可观察的误触路径、用户证据或已有交互约束支持。
  说明谁受益、谁多付出什么，并用对应场景复验。风险路径分析不等于实测误触率下降，缺用户数据就注明。
- 仅为美观增加负担不接受；不能以卡片更多或点击更少抵消文字难辨、目标缩小、关键操作消失、
  安全保护被削弱或数据契约回退。取舍超出用户范围或依据不足时，保留现状或请求必要选择。
- 新页面没有改前基线时，报告是否满足预定任务条件，不宣称效率提高了多少。

### 根据组件职责选择场景

| 受影响职责 | 按风险选取的条件与事件 | 应能证明什么 |
|---|---|---|
| 列表、批量、分栏与滚动 | 空/少量/长数据，长标签或错误项，开始/中段/末尾，改动涉及的断点 | 目标可定位，内容和动作不被遮挡；滚动、吸附与对齐符合本次布局决定 |
| 表单、输入与提交 | 正常/错误，提交中/失败重试，短视口或软键盘，长输入 | 主操作与错误可达，输入和上下文保留，重复提交与重试符合原契约 |
| 弹窗、菜单和选择器 | 打开/关闭/取消，键盘路径与焦点返回，禁用/忙碌 | 触屏与键盘均能完成任务，不出现焦点丢失、遮挡或无意触发 |
| 主题、动效与反馈 | 受影响明暗主题，成功/错误反馈，减少动态效果，连续效果的暂停/恢复 | 信息仍可读、可操作，效果不阻塞任务；具体平台只以对应平台证据验收 |

无需固定要求所有页面等高、所有列表吸顶或所有状态截图。每个选中场景都应有可观察成功条件，
并匹配证据：实际操作验证路径，截图验证呈现，几何/样式测量验证边界，工程测试验证行为契约。
没有工具或环境时标为未验证；已知重要回退先修复，不能只展示成功状态就宣布通过。

## 视觉质量审查闭环

适用于新建页面和明显视觉重构。局部修改只检查受影响区域及关联状态；
纯文案或非视觉任务不强制跑整页审美审查。

1. **实现前建立问题基线。** 按 [任务与场景验收](#task-acceptance) 确定成功条件，结合设计简报明确主要任务、预期阅读/操作顺序和设计约束。
   已有页面尽可能运行并看截图，记下应保留的有效设计与待改善问题；
   新页面或运行受阻时，标记为设计目标/代码假设，不伪造“改前截图结论”。
2. **运行并观察实际结果。** 使用项目已有启动和浏览器工具，等数据、字体、焦点或动画达到可观察状态后截图，
   实际打开查看。记录路由、视口、主题、数据/交互状态及截图位置；覆盖相关手机、桌面与状态，
   不要求机械拍摄所有组合。DOM 文本、截图文件存在、尺寸元数据、构建通过都不是视觉通过。
3. **先观察，再判断。** 指出视觉最先吸引注意的区域，它是否匹配任务优先级；
   对照下表检查，保留有效设计，区分可观察缺陷、需运行验证的假设和个人风格偏好。
   不用“高级一点”“更现代”作为修复理由，不为写审查意见捏造问题。
4. **把问题转成修复。** 记录“区域/状态 → 观察与证据 → 用户影响 → 最小可执行调整 → 复验条件”。
   先解决阻碍操作、可访问性、内容溢出或主次混乱，再处理确有收益的局部细节。
   一次处理有共同原因的小组问题；需要新组件时回到组件决策，不直接加装饰。
5. **复验并停止。** 修复后在可比的路由、视口、主题与数据状态重新运行、截图并查看，
    同时检查受影响交互和工程回归，逐项记录选中场景的结果。主要任务清楚、相关状态完整、已发现的重要问题解决，
   且剩余建议只是偏好或低收益时停止；本已优秀则不必制造改动。
   超出范围、缺少授权或运行条件时说明阻碍与剩余风险，不无限美化，也不把未验证项算通过。

| 检查维度 | 从真实页面检查什么 | 可执行的改进方向（非固定方案） |
|---|---|---|
| 布局与层次 | 主任务/结果是否易发现；视觉权重是否与内容优先级一致；是否有竞争焦点 | 调整位置、分组或主次权重；不自动增设 Hero/卡片 |
| 字体与内容 | 标题、标签、正文、辅助信息是否可区分；行长/行高是否适合阅读；真实内容是否足够 | 调整类型尺度、字重、文字组织；不靠营销占位文案填充 |
| 间距与密度 | 对齐、节奏、分组距离是否一致；留白是否有用途；密集数据是否可扫描 | 调整容器宽度、组间距、布局或渐进披露，而非缩小所有控件 |
| 色彩与表面 | 角色是否一致；文字/焦点是否清楚；装饰是否干扰内容或偏离设计系统 | 修正相关 token、对比或表面层级，而非整体改成黑白 |
| 状态与交互 | 加载/空/错/成功是否解释当前情况与下一步；hover、focus、禁用与操作边界是否明确 | 修复就近反馈、状态表达和焦点；截图之外另测键盘与实际交互 |
| 操作效率 | 同一任务从查找、理解到操作与错误恢复的整体成本，以及证据是否支持收益 | 按任务成本标准记录取舍；步骤和密度改善不能抵消正确性、可读性或可达性回退 |
| 响应式与一致性 | 长文本、窄屏、弹窗是否溢出；同类组件/主题是否一致；动效后布局是否稳定 | 局部调整约束与断点，复验相邻区域；不顺带重构业务 |

最小审查记录可直接放在任务记录/交付中，无需新增报告文件：
`证据类型（真实截图/代码推测）｜路由、视口、主题、状态｜保留项｜问题及影响｜修复/不改理由｜复验结果`。
浏览器不可用时，应记录尝试、具体障碍与待检查项，交付明确写“未完成浏览器/视觉验证”。
用户提供截图可支撑该截图中的观察，但不能证明当前代码渲染、隐藏状态或交互已验证。

## 工程完成标准

按风险选择最小充分证明，不要求每个文字修改都重做所有用例：

- 主流程仍满足原输入、输出、批量、导出与取消契约；UI 重试不盲目重复有副作用的请求。
- 任务场景逐项有结果，效率结论与证据相符；必要确认保留，不把未经验证的取舍包装成效率提升。
- 项目支持且受影响的主题（含浅色/纯白和深色）中，加载、空、成功、错误、禁用和确认弹窗均可理解。
- 相关测试与构建通过；浏览器无新增脚本错误或 CSP 违规。构建、mock、真实接口与真实副作用分开报告。
- 窄屏约 375px、桌面及必要的横屏布局可用；长邮箱/文件名/错误不会撑破布局。
  数据表的局部滚动需有明确边界，不能变成整个页面无意溢出。
- 控件有标签与焦点；键盘 Tabs/菜单/弹窗可用，取消和关闭返回合理焦点。
  等待 React/Radix 的最终状态或关闭动画，用可重试断言，不以任意 sleep 代替条件等待。
- 主题偏好刷新保留、存储不可用有退路、减少动态效果生效；不为外观放宽 CSP。
- 所用组件来源、匹配版本、实际 API 与许可可追溯；无重复原语、无伪称官方、无不必要的新依赖。
- 截图只含虚构/脱敏数据；凭证不进入代码、示例或本技能。mock 不授权真实账号操作或部署。
- 交付明确已测/未测；只清理本任务已确认无用的临时产物，保留源码、用户数据与必要证据。

## 维护时的情境检查

维护本技能时按改动选择受影响的 A–F 情境；执行策略或全流程变更再覆盖全部。
先用输入条件走读规则，再按具备的条件运行实际任务；
将结果分开记录为“规则检查：通过/失败”和“实际行为：通过/失败/未运行”。
规则通过须能指出支持该决定的入口/参考位置，且相关专项参考没有相反约束；
实际通过须有表中证据。任一失败条件出现则该项失败，缺证据不能判实际通过。
结构测试、人工规则走读、独立代理执行和浏览器视觉验证互不替代。

| 情境与输入条件 | 必须观察到的决定与验收证据 | 失败条件 |
|---|---|---|
| **A 简陋工具页**：只有标题、输入和大空白；已有粘贴、处理、结果/导出功能；要求提升完成度 | 从任务提出布局取舍与简要构图，选定空/结果/错误/长数据等相关场景；先查项目再初筛候选，核验入选来源；改后截图和交互支撑功能与效率结论 | 只换颜色或圆角；把选库记录当作布局决定；因“极简”跳过有效候选或默认堆装饰 |
| **B 成熟设计系统**：已有品牌色、token、组件和主题；要求改善一页 | 决策与差异说明复用了哪些 token/组件；受影响截图与相邻页面保持同一语言；新增依赖有缺口与收益证据 | 强制纯白/黑白主按钮；创建平行主题；重装职责相同的主库 |
| **C 明确极简**：用户要求极简、少装饰且功能完整 | 以排版、分组、主次与反馈形成完成度；按整体成本解释入口和密度，截图/交互证明任务与状态清楚；装饰可拒绝 | 强制动画/渐变；隐藏常用操作或缩小目标后仅以点击数不变、卡片增多宣称效率提升 |
| **D 复杂后台**：真实多模块、数千行数据、筛选、详情、批量操作 | 导航/筛选/数据/操作按业务组织；验证筛选、选择、详情、批量与窄屏边界；截图显示可扫描的数据密度，复杂功能库按真实需求选择 | 为简洁隐藏必要操作、把表格挤进窄卡片、虚构图表数据或用展示模板替代业务结构 |
| **E 局部修改**：只修手机弹窗溢出，桌面与现有主题保持 | 走快路径，差异限于相关布局；核验短视口、相关主题、焦点与关闭返回，无新能力缺口时零上游获取 | 借机换库、重做主页或全库下载；要求完整设计稿、逐库拒绝记录才允许局部修复 |
| **F 已经优秀**：现有层次、密度、状态及交互符合目标，要求检查是否值得提升 | 审查记录指出有效设计与验证范围；无明确收益时结论为保留，允许零代码改动、零新依赖；不制造候选或问题来证明工作量 | 强制添加视觉组件/动画，反复改变已达标设计；未看截图却宣称视觉优秀 |

相关工程边界继续检查：

- 删除主题：入口、类型、样式、持久化与初始化一致，旧值安全回退；业务数据不受影响。
- HeroUI / React Bits：许可和对应主版本已核对，不照搬旧 Provider/API，不注册无关 MCP，
  不整体安装演示站；可从设计阶段选组件，不要求先做固定白/深页面。
- 状态与动作相接：默认、悬停、焦点、长文本和窄屏实际边界分离，触摸目标仍可用。
- 局部特效调整：只改请求维度，减少动态效果/离屏降级可用，不擅自改数量、速度或轨迹。
- 来源不可核验或浏览器不可运行：记录缺口，可继续不依赖缺失能力的工作，不伪造源码/截图通过。
- 公开维护：使用可移植路径，不包含私人运行记录；结构和源码管理回归测试通过。

只维护会改变决策且能验收的规则，不把本文件扩成通用设计教材或运行日志。
